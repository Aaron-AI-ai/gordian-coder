f-review 커밋 기준 리뷰 한눈에 보기
/f-review [커밋/범위] [--files=...] — 대상을 어떻게 지정하느냐에 따른 5가지 경우
대상 = (커밋 diff 파일) ∪ (--files) − exclude
기본값

인자 없음

/f-review
→ HEAD~1..HEAD

최근 커밋 1개만 리뷰. 커밋을 만든 직후 바로 확인할 때.

HEAD

단일 커밋

/f-review HEAD /f-review a1b2c3d
→ <ref>~1..<ref>

특정 커밋 하나만 콕 집어 그 변경분만 리뷰.

범위

A..B

/f-review main..feature/x
→ A..B (그대로)

A와 B 두 커밋 사이 diff 전체를 리뷰. main과 갈라진 뒤 feature에 쌓인 변경분 전체.

from/to

범위 분리 지정

--from=main --to=feature/x --from=v1.2.0
→ A..B / A..HEAD

to 생략 시 HEAD까지. bare 범위와 결과 동일.

파일만

커밋 없이 --files

--files=A.java,B.java
→ 커밋 diff 없음 (파일 모드)

지정 파일 자체가 대상, 전체 파일 검토. 아직 커밋 안 한 작업 중 파일에 적합.

fcq true 계획(plan) 단계에서 fcq 정적 분석을 1회 실행해, 위반 사항을 리뷰어 증거로 주입하고 최종 리포트에도 병합.
fcqFix true fcq 위반 전체(사소한 MINOR 포함)에 대해 f-fixer 서브에이전트가 TO-BE 수정 코드를 작성하는 픽스 패스를 추가.

f-judge 평가 기준 한눈에 보기
제출된 리뷰(findings)를 코드와 대조해 채점 — 코드가 아니라 "리뷰의 품질"을 평가
5개 기준 가중합 ≥ 70점 → PASS, 미만이면 REWORK (최대 2회 재리뷰)
40%

Validity 타당성

finding을 코드와 대조해 적대적으로 반박. 코드와 안 맞으면 무효.

20%

Coverage 커버리지

변경의 주요 부분을 빠짐없이 봤는지. 안 본 곳은 coverageGaps로 표시.

15%

Evidence 근거

"문제가 될 수 있다"가 아니라 구체적 실패 시나리오를 제시했는지.

15%

Severity 심각도 보정

blocker/major가 진짜 그 정도인지, 실제 결함을 축소하지 않았는지.

10%

Actionability 실행 가능성

blocker/major마다 실제 수정안(asIs → toBe)이 달려 있는지.

finding 개수로 가점 없음(0건도 100점 가능) · 중복·과장 지적은 감점 · 위양성보다 위음성 선호
