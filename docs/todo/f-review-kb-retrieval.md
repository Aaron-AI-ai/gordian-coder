## 3. 개선 후보 (우선순위 순)

### 3.1 [B] 식별자를 단서로 추가 — 빠른 안

- 내용: 필드·상수 이름(`SVC_ID`)을 camelCase로 정규화(`svcId`)해 단서에 추가한다. `svcId`는 몇 개 문서에만 나오는 희귀 용어라 `PBTransactionAspect.md` 등이 올라온다.

### 3.2 [A] 에스펙트 적용 조건 색인 — 근본안

- 내용: KB의 에스펙트 문서에서 포인트컷 표현(`bean(*Service)`, `execution(public * kr.co..*Controller.*(..))`, `args(commonRequest,..)`)을 뽑아 색인하고, 리뷰 파일의 클래스 이름·어노테이션이 포인트컷에 맞으면 그 문서를 주입한다.
- 효과: 자동 적용되는 규칙 전반(case-39의 `*Controller`, case-95의 `*Service`)이 같은 방식으로 풀린다. 설정 없이 문서가 늘면 같이 늘어난다.
- 작업: 포인트컷 문법(`bean`, `execution`, `args`)의 부분 해석, 색인 캐시, 테스트.
- 위험: 구현이 중간 규모. 포인트컷 해석이 불완전하면 누락/과주입.

### 3.3 [D] KB 문서에 검색 힌트 필드 (md 보강)

- 내용: 문서 front-matter에 선택 필드를 추가하고 색인에서 높은 가중치를 준다.
  - `search_when`: 이 문서를 찾아야 하는 상황(자연어/코드 조각)

- 작업: 우선 `ExtTransactional`, `RetryableRestTemplate`, `KafkaConsumerService`부터 채움. KB 생성 템플릿(`reference_agent`)에 필드를 추가하거나 기존 문서에서 초안을 만들어 검토.
- 주의: KB는 `test-projects` 저장소 자산이라 수정 시 그 저장소 커밋이 필요 (push는 GitLab 403으로 막혀 있음).

자료 전체(`AUTO_EVIDENCE_MAX_CHARS` 30,000)는 이미 꽉 차 있다. 5개 파일 중 3개가 30,000자에서 잘렸고, 각 구간의 크기는 다음과 같았다.

PoC 코드 기준이 이렇다. 실제 업무 코드는 import·단서·줄 수가 더 많으니 문제가 더 커진다.

**원인** (`src/core/review/evidence/dossier.ts`, `framework-kb.ts`)

1. **예산이 넘치면 거기서 멈춘다.** `fitSection`은 예산을 처음 넘는 문서에서 끝난다. 뒤에 짧아서 들어갈 수 있는 문서(예: `ExtTransactional.md` 2.3k)가 있어도 같이 버려진다.
2. **사전 검색 결과가 늘 맨 뒤다.** 순서가 `[...importDocs, ...prefetch]`로 고정이다. import 문서가 3개를 넘으면 사전 검색 결과는 하나도 들어가지 못한다.
3. **import 문서를 중요도로 고르지 않는다.** 파일에 적힌 import 순서대로 앞의 6개(`KB_MAX_DOCS`)만 쓴다. import가 6개를 넘으면 나머지는 후보에도 오르지 못한다.
4. **분할 리뷰에서 모든 세그먼트가 같은 문서를 받는다.** 1,000줄을 넘는 파일은 세그먼트로 나눠 리뷰하지만, KB 자료는 실제 파일 경로 기준으로 한 번만 만들어 캐시한다(`pipeline/prompt.ts:32`). 단서도 파일 전체에서 뽑으므로 세그먼트와 상관없이 같은 3개가 들어간다.
5. **`ReviewEvidence.docs`가 실제 주입 문서가 아니다.** 예산을 통과한 문서가 아니라 후보 전체를 기록한다. 그래서 디버그 결과로는 몇 개가 실제로 들어갔는지 알 수 없다.

**검토한 대안: 예산 증액 (KB 18k→30k 이상, 전체 30k→45k 이상) — 보류**

- 순서 문제는 그대로 남는다. SONAQ009의 후보만 합쳐도 약 43k라서, KB 구간을 두 배인 36k로 늘려도 앞쪽 import 문서만 남는다.
- 자료는 `system.transform` 훅으로 모델 턴마다 다시 들어간다. 파일당 10~17턴이므로, 1만 자를 늘리면 파일 하나에 최대 약 17만 자를 더 보내는 셈이다. 이 비용이 파일 수와 deepPasses 수만큼 곱해진다.
- 후보 수는 코드 크기에 비례해 늘지만 예산은 한 번 늘리면 끝이다. 큰 코드로 갈수록 효과가 떨어진다.

**개선안 (순서대로)**

1. **[E1] 작은 수정**
   - `fitSection`이 예산을 넘는 문서는 건너뛰고 다음 문서로 계속 가게 한다.
   - `docs`에 예산을 통과한 문서만 담는다.
2. **[E2] 사용 빈도 정렬 + 2단 주입 (핵심)**
   - import 문서와 사전 검색 결과를 한 목록으로 합친다. 소스에서 해당 클래스 이름이 나온 횟수 순으로 정렬한다.
   - 위에서부터 예산 안에 드는 문서는 **전문**을 넣는다. 나머지는 **한 줄 색인**(경로 + description, 약 200자)으로만 넣는다. `kbSearch`가 상위 2개는 전문, 나머지는 제목만 주는 방식을 그대로 가져온다.
   - 색인에는 "필요하면 `kb_search("<클래스명>")`로 전문을 조회하라"는 안내를 붙인다. 클래스 이름이 파일 이름과 정확히 같으면 +5점이라 대부분 1위로 나온다.
   - 색인 단계에서는 `KB_MAX_DOCS` 6개 제한을 푼다. 그러면 import 수와 관계없이 관련 문서가 있다는 사실은 모두 모델에게 전달된다. 문서 20개도 약 4k라 전체 상한 안에 들어간다.
3. **[E3] 세그먼트별 순위**
   - 후보 목록은 지금처럼 파일 단위로 캐시한다. 사용 빈도만 현재 세그먼트 범위 안에서 다시 세서 전문으로 넣을 문서를 고른다.
   - 세그먼트마다 사전 검색을 다시 돌리는 것보다 수정이 작다.
4. **[E4] 예산 증액 (측정 후 필요하면)**
   - E2·E3 뒤에도 "전문이 필요한데 예산 때문에 색인으로만 들어간" 케이스가 확인될 때만 한다.
   - 그 경우에도 소폭(KB 18k→24k, 전체 30k→36k)만 늘린다. git 이력이 잘리지 않게 하려면 약 2~3k의 여유가 필요하다.

**측정**

- 스크래치 스크립트 2개를 썼다.
  - `kbbig.ts`: 파일별 후보와 실제 주입 결과
  - `kbsec.ts`: 자료 구간별 크기와 잘림 여부
- 개발할 때 `scripts/`로 옮기거나 테스트로 만들어 전후를 비교한다. f-review 평가의 KB 케이스로 회귀도 확인한다.
- 실제 업무 코드 중 큰 파일을 대상으로 다시 측정해야 한다. 로컬에는 on-stk-ord보다 큰 fico 코드가 없다.

### 3.7 [Q] `kb_search` 결과 품질 (실제 호출 로그 기준)

2026-10-20~21 OpenCode 세션(`~/.local/share/opencode/opencode.db`)에서 `kb_search` 호출 36건을 확인했다.

- **검색어가 길면 엉뚱한 문서가 올라온다.**
  - 사례: `SimpleDateFormat date format DateTimeFormatter`로 검색하면 1위가 `FormatterUtils.md`(고정길이 전문 유틸)다. 단어 `format`·`formatter`가 이 파일 이름에 포함돼 점수를 받기 때문이다.
  - 같은 파일에서 사전 검색은 `SimpleDateFormat` 한 단어로 `DateUtils.md`를 맞혔다.
  - 개선: 도구 설명에 "클래스·식별자 이름 하나"를 명시한다. 검색어에서 다른 단어를 포함하는 짧은 단어는 가중치를 낮춘다.
- **일반 개념어로 검색하면 무관한 전문이 들어온다.**
  - 사례: `Optional`, `Autowired`, `singleton`. 본문에 한 번만 나와도 결과가 나와서 0건으로 처리되지 않는다. 그래서 반복 검색 차단 장치도 걸리지 않고, 관련 없는 문서 전문 2개(최대 12k)가 들어간다.
  - 개선: 메타 점수가 0이고 본문 언급만 있는 문서는 결과에서 빼거나 제목만 보여 준다.
- **사전 검색으로 이미 주입한 문서를 다시 받는다.**
  - 사례: `RestTemplate` 검색 1위가 이미 주입된 `RetryableRestTemplate.md`다.
  - 개선: 리뷰 상태에서 이미 주입한 경로를 결과에서 빼거나 제목만 보여 준다.
- **파일 이름이 같으면 하나만 색인된다.** `indexDocs`가 소문자 파일 이름을 키로 쓰고 먼저 찾은 것만 남긴다. 다른 폴더에 같은 이름의 문서가 있으면 `kb_search`와 import 대체 경로 양쪽에서 보이지 않는다.

## 5. 별도 정리 항목 (평가 자산)

- **대조군이 내장 `@Autowired` 규칙과 충돌**: `control-01`(`AcntCleanQueryService`)이 `@RequiredArgsConstructor` + `private final` 주입을 써서, 내장 규칙(`knowledge/framework.md`: `@Autowired` 필드 주입)상 `framework` major가 나와 FAIL. `control-04`(`@RequiredArgsConstructor` 사용) 등 다른 대조군도 같은 문제일 수 있음. 대조군 코드를 규칙에 맞게 고치는 새 커밋 필요 (기존 태그 이동 금지).
- **정답 YAML 정책**: 프레임워크 KB에서 나온 위반은 리뷰어가 `framework`로 분류하는 경우가 많다. KB 케이스는 처음부터 `framework`를 함께 허용하도록 정리 (이미 case-63/66/68/94/97 적용).
