# f-log — 에러 로그 분석

Spring Boot 서비스의 Java 스택트레이스를 받아 **문제 코드 위치 · 원인 · 해결 방안**을
제시한다. 인터넷이 없는 환경에서 동작하므로 웹 검색은 쓰지 않고, 저장소 코드와
사내 KB만을 근거로 삼는다.

## 0. 전체 그림

실선 = 1차 구현 범위, **점선 = 추후 도입**.

```
  로그 붙여넣기 ─┐
                │
   OpenSearch ┄┄┤            ┌──────────────┐
(추후 적용 예정)│            │ 1. f_log_    │       스택 파싱 → 프레임 분류
                └───────────►│    plan      │       → 용의 파일 확정
                             └──────┬───────┘
                                    ▼
   프레임워크 KB ───────────►┌──────────────┐
   (framework-kb.ts)         │ 2. 분석 루프 │◄──┐   원인 도출 + 해결 방안
   저장소 코드 ─────────────►│   context    │   │
   (read/related/imports)    │   → submit   │   │
                             └──────┬───────┘   │
   사례 KB (Jira) ┄┄┄┄┄┄┄┄┄┄┘       │           │
   별도 참고 서버 (추후 적용 예정)  ▼           │
                             ┌┄┄┄┄┄┄┄┄┄┄┄┄┄┄┐   │
                             ┊ 재현 검증    ┊   │   ①원인만 → 테스트 작성 → red
                             ┊ f-log-verify ┊   │   ②해결안 → 적용 → green
                             └┄┄┄┄┄┄┬┄┄┄┄┄┄┄┘   │   (추후 적용 예정 — 1.3)
                                    ▼           │
                             ┌──────────────┐   │
                             │ 3. 심사      │   │   원인·해결안이 실제 로그와
                             │   judge      │   │   연관 있는가
                             └──────┬───────┘───┘   rework: 기각하고 다른 가설로 (1.2)
                                    ▼
                             ┌──────────────┐
                             │ 4. finalize  │       누락 검증 → 리포트
                             └──────────────┘
```

## 1. 파이프라인 — 4단계

에러 로그 한 건을 받아 원인과 해결 방안을 내놓기까지 네 단계를 거친다. 분석과 심사
사이에 재현 검증을 끼울 자리를 비워두되, 1차 범위에는 넣지 않는다(1.3).

| 단계 | 도구 | 하는 일 |
|---|---|---|
| 1. plan | `f_log_plan` | 로그 파싱 → 프레임 분류 → 용의 파일 확정 |
| 2. 분석 | `f_log_context` → 루프 → `f_log_submit` | 원인 도출 + 해결 방안 |
| ┄ 검증 | `f_log_verify_*` | 재현 테스트 red→green (**추후 적용 예정**, 1.3) |
| 3. 심사 | `f_log_judge_context` → `f_log_judge` | 원인·해결안이 실제 로그와 연관 있는지 판정 |
| 4. 종료 | `f_log_finalize` | 누락 검증 → 리포트 (1.4) |

심사의 합격/재작업 판정은 점수 임계값으로 **코드에서** 계산하고, 재작업 횟수를 상한으로
막는다. 판정 엔진은 `pipeline/judge.ts`를 재사용하되 제출 스키마와 rework 처리는
f-log 전용이다 — 1.1, 1.2.

### 1.1 심사 — 무엇을 판정하는가

심사는 **원인 하나가 참인가**를 묻는다. 판정 축은 셋이다.

| 축 | 묻는 것 |
|---|---|
| **관측 대조** | 로그의 관측(스택 순서, 예외 메시지의 값, 반복 여부)을 원인이 각각 설명하는가 |
| **대안 배제** | 다른 가능성을 검토했는가 |
| **원인 제거 vs 증상 완화** | 해결안이 원인을 없애는가, 증상만 덮는가 |

### 1.2 rework — 기각하고 다른 가설로

rework는 "다시 더 잘 보라"가 아니라 **"가설이 틀렸으니 다른 가설로 가라"**다. 그래서
화살표는 분석 단계로 되돌아간다(0절).

다듬는 것이 아니라 기각하고 이동이므로 **기각된 가설이 누적되어야** 다음 라운드가 같은
결론으로 되돌아오지 않는다. 재사용하는 구현은 최신 verdict의 feedback 하나만 주입하므로,
f-log는 기각 목록 전체를 주입한다. `judge-store`의 `attempts[]`에 라운드별 기록이 이미
쌓이므로 저장소는 그대로고, 주입부만 누적으로 바꾼다.

### 1.3 재현 검증 — 추후 적용 예정 (점선)

원인을 글로 설명하는 대신 **코드로 증명하는 단계**다. 도출한 원인이 맞다면 그 조건에서
실패하는 단위 테스트를 짤 수 있어야 한다. 그 테스트를 실제로 만들어 돌려보고, 해결안을
적용한 뒤 다시 돌린다.

```
원인 → 재현 테스트 작성 → 실패(red) 확인 → 해결안 적용 → 통과(green) 확인
```

red가 안 나오면 원인이 틀린 것이고, green이 안 나오면 해결안이 틀린 것이다. 추론이
아니라 실행 결과로 판정하므로 심사의 근거가 훨씬 단단해진다.

**지금은 만들지 않는다 — 모델 성능이 따라오지 못한다.** 테스트 작성 → 빌드 → 결과
해석 → 해결안 적용 → 재실행은 긴 다단계 사슬이고, 소형 모델이 그 중간에서 무너지는
것이 이미 관측돼 있다(`framework-kb.ts`: 작은 모델은 조회를 한 번도 하지 않고 제출한다.
`fixer.ts`: file_read를 받은 fixer가 같은 오류에 35번 재시도했다). 여기에 빌드 환경
의존까지 겹치므로 1차 범위에서 제외한다.

### 1.4 누락 검증 — 로그를 다 소화했는가

원인 하나를 잘 찾았더라도 **로그의 나머지를 안 본 채 끝났을 수 있다.** 종료 단계에서
집합 비교로 확인한다. 세 가지를 본다.

| 항목 | 판정 방법 |
|---|---|
| **다루지 않은 예외 체인** | 로그에서 파싱한 예외/`Caused by` 목록 중 어떤 원인으로도 설명되지 않은 것 |
| **열어보지 않은 용의 프레임** | plan이 저장소 안으로 해석한 프레임 중 분석에서 한 번도 읽히지 않은 파일 |
| **설명되지 않은 관측** | 심사(1.1)의 관측 대조에서 미해결로 남은 항목 |

앞의 두 가지는 **코드가 집합 차집합으로 판정**한다 — 모델 판단이 아니다.

누락이 있으면 되돌리지 않고 **리포트에 명시**한다. 종료 단계에서 다시 루프로 보내면
종료 조건이 흐려지고, "무엇을 못 봤는지 아는 리포트"가 "다 봤다고 주장하는 리포트"보다
안전하다. 분석 자체를 다시 돌릴지는 그것을 읽은 사람이 정한다.
