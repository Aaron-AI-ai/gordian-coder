# 단위 테스트 검증 규칙

## 자기 점검 (테스트를 쓴 뒤, 검증 스크립트를 돌리기 전에)

1. 모든 테스트 메서드에 의미 있는 단언이 있는가 (반환값/상태 단언 + 필요한 `verify`). `assertNotNull`만 있으면 실패다.
2. 케이스가 `docs/f-unit-test-case-rule.md`대로인가 (정상 2건은 서로 다른 경로, 경계값은 코드의 비교·한도에서, 예외는 코드에 실제로 있는 예외 타입과 코드값).
3. mock 스텁이 호출 인자와 맞는가 (쓰이지 않는 스텁, 스텁 없는 mock이 돌려준 `null`로 인한 NPE).
4. `@BeforeEach`/`@AfterEach`/`@Transactional`이 모두 있고 테스트 간 상태 공유가 없는가.
5. (Mapper) 인터페이스에 선언된 **모든 메서드**를 계획된 `<MapperName>Test`에서 `.<메서드>(`로 호출하는가, `@Commit`·`@Rollback(false)`·`Propagation` 변경이 없는가.
6. 컴파일에 필요한 import와 VO 필수 필드를 놓치지 않았는가.

## 검증 실행

macOS/Linux:

```
sh scripts/run-coverage.sh --module <gradle 모듈> --tests <FQCN,FQCN,...> --out <디렉터리>
```

Windows (PowerShell, 경로는 슬래시):

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run-coverage.ps1 -Module <gradle 모듈> -Tests <FQCN,FQCN,...> -Out <디렉터리>
```

| `run-coverage.sh` | `run-coverage.ps1` | 의미 |
|---|---|---|
| `--module` | `-Module` | Gradle 모듈 (`a`, `a/b`, `:a:b`, `a:b`) |
| `--tests` | `-Tests` | 테스트 클래스 FQCN, 쉼표 구분 |
| `--out` | `-Out` | 결과 디렉터리 (이전 결과는 먼저 지운다) |
| `--project` (선택) | `-Project` (선택) | 프로젝트 루트, 기본값은 현재 디렉터리 |

두 스크립트는 같은 파일을 만든다. Windows는 PowerShell 스크립트를 쓴다.

결과 디렉터리에 `status.json`, `jacoco.xml`, `jacoco-html/`(사람이 보는 줄별 커버리지, 읽지 말 것), `test-results/`, `gradle.log`가 생긴다.

- 스크립트는 Gradle을 먼저 오프라인(`--offline`, Gradle 캐시)으로 돌리고, 오프라인 실행이 의존성 해석 실패이거나 운영 소스(`src/main/java`)의 javac 오류일 때만 온라인으로 한 번 더 돌린다. 테스트 소스(`src/test/java`)의 javac 오류는 온라인으로 다시 돌리지 않는다. `--refresh-dependencies`는 쓰지 않는다(모든 의존성을 다시 해석해 저장소 요청 제한에 걸린다).
- 의존성·네트워크 실패(`Could not resolve`, Nexus의 `status code 429` 등)는 환경 문제다. 사용자에게 알리고 멈춘다. 테스트 코드로 "고치지" 않는다. 확인 항목은 두 가지다.

1. **빌드(컴파일) 성공.** 실패하면 오류 메시지의 파일·줄을 보고 테스트 코드를 고친 뒤 다시 돌린다(컴파일 재시도는 보강 횟수에 포함하지 않는다).
2. **대상 클래스의 JaCoCo 라인·분기 커버리지** (목표 100%).

**이번에 생성한 테스트는 모두 통과해야 한다.** 실패하면 플러그인이 execute로 돌려보낸다(수정 재시도 횟수에 포함). 대상 코드를 다시 읽고 테스트의 기대값·입력·기대 예외를 코드의 실제 동작에 맞게 고친다. 운영 코드는 고치지 않고, 테스트를 지우거나 이름을 바꾸거나 `@Disabled`로 끄지 않는다. 코드가 틀렸다고 판단되면 그래도 현재 동작을 단언하고, verify `note`에 결함 의심으로 적는다(리포트에 남는다).

**기존 테스트의 통과 여부는 검증 항목이 아니다.** 실패한 기존 테스트는 끄지 않고(`@Disabled` 금지), 운영 코드도 고치지 않는다. 기존 테스트는 계획의 `update_existing`으로 승인받은 것만 기대값을 고친다(아래). 실패해도 커버리지에는 반영된다. 리포트(`report.md`)의 "실패한 테스트"에는 플러그인이 `test-results/`를 읽어 원인을 적는다.
- **기존 테스트**(이번 실행 전부터 있던 것)와 **이번에 생성한 테스트**를 나눠서 적는다.
- **변경으로 깨지는 기존 테스트:** 계획 단계에서 대상 파일의 기존 테스트를 바뀐 코드와 대조해, 이번 변경 때문에 기대값이 맞지 않게 되는 테스트를 `update_existing` = [{ file, test, reason }]에 적고 계획 `note`에도 같은 목록(무엇이 바뀌었고 새 기대값이 무엇인지)을 보여 승인받는다. 승인된 테스트는 기대값(필요하면 입력)만 새 동작에 맞게 고치고, 삭제·이름 변경·`@Disabled`는 하지 않는다. 변경이 의도인지 회귀인지 확신할 수 없으면 계획에 그렇게 적고 사용자가 정하게 한다.
- 목록에 없는 기존 테스트는 그대로 둔다(형식이 낡은 테스트 포함). 플러그인이 계획 시점 본문과 비교해, 바뀌었으면 되돌리라고 돌려보낸다. 실행 뒤에 목록에 없던 기존 테스트가 실패하면 고치지 말고 리포트에서 확인을 요청한다. 고친 기존 테스트는 리포트의 "수정한 기존 테스트"에 사유와 함께 남는다.
- 각 항목에 기대값·실제값(또는 예외 종류와 메시지)과 실패한 테스트 줄을 함께 적는다.
- 요약(`note`)에서 실패한 테스트를 다시 풀어 쓸 필요는 없다. 이번에 생성한 테스트는 통과할 때까지 고친다. 수정 재시도를 다 쓰고도 실패하면 리포트에 남는다.

## Mapper 대상은 JaCoCo로 재지 않는다

Mapper 인터페이스에는 JaCoCo가 잴 코드 줄이 없다(SQL은 XML에 있다). 그래서 Mapper 대상은 커버리지 판정에서 **제외**하고, 대신 정적 점검한다: 인터페이스에 선언된 모든 메서드(`default`/`static` 제외)가 테스트 파일에서 `.<메서드>(`로 호출되어야 한다. 빠진 메서드는 결함이며 컴파일 오류처럼 execute로 되돌아가 고친다(수정 재시도를 쓰고 커버리지 보강 횟수는 쓰지 않는다).
리포트에는 "커버리지 측정 안 함 (XML SQL은 JaCoCo가 보지 않음)"으로 적고 메서드별 호출 여부를 남긴다.

## 커버리지 공백 보강 (최대 3회)

`jacoco.xml`에서 대상 클래스의 `<line>`(`mi`>0 또는 `mb`>0)와 `<counter type="BRANCH">`를 읽는다.

- 라인 미커버(`mi>0`): 그 줄이 속한 분기 조건을 읽고, 그 줄에 도달하는 입력·스텁으로 케이스를 추가한다.
- 분기 미커버(`mb>0`): `if`/삼항/`&&`·`||`의 어느 쪽이 빠졌는지 보고 반대쪽 케이스를 추가한다.
- 보강은 기존 테스트를 지우거나 고치지 않고 케이스를 **추가**한다(기존 테스트 수정은 승인된 `update_existing`만). 한 번 보강한 뒤 다시 검증 스크립트를 돌린다.

3회 뒤에도 빈 곳이 있으면 멈추고 남은 라인·분기를 리포트에 적는다(커버리지 미달은 완료를 막지 않는다).

## 도달 불가능한 분기

방어 코드처럼 입력으로 도달할 수 없는 분기(예: 앞에서 이미 null을 걸러낸 뒤의 null 검사, 프레임워크가 보장하는 조건)는 억지로 채우지 않는다.
리포트의 `note`에 **클래스·줄·사유**를 적는다: `SONAQ001Service:78 — checkParameter가 먼저 걸러 도달 불가`.
도달 가능한데 어려워서 남긴 것은 사유가 될 수 없다.
