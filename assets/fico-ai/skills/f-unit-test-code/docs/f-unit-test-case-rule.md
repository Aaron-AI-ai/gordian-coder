# 단위 테스트 케이스 규칙

대상 클래스의 **public 메서드마다** 아래 케이스를 만든다. 케이스는 코드를 읽어 도출한다(요구사항을 추측하지 않는다).

| 케이스 | 이름 | 도출 방법 |
|---|---|---|
| 정상 1 | `<메서드>_normal1` | 기본 성공 경로. 반환값과 mock 호출(`verify`)을 단언한다. |
| 정상 2 | `<메서드>_normal2` | **정상 1과 다른 입력이나 다른 분기**(예: 값이 0, 목록이 여러 건, 선택 필드 있음/없음). 같은 입력의 복제 금지. |
| 경계값 | `<메서드>_boundary` | 코드의 `<`, `<=`, `>`, `>=`, `==`, 길이·크기 제한, `null`/빈 문자열/빈 목록 검사에서 도출. 경계의 양쪽을 본다(예: `isEmpty()`면 `""`, 길이 제한이면 한도와 한도+1). 비교 연산이 없는 메서드도 `_boundary`를 만든다(아래 "비교 연산이 없는 메서드의 경계"). |
| 예외 | `<메서드>_exception` | 코드의 `throw`(예: `PBOnlineException.create("1001", ...)`)와 mock이 던지는 예외(`when(...).thenThrow(...)`)에서 도출. 코드에 없는 예외 타입은 기대하지 않는다. |

**모순된 테스트를 남기지 않는다.** 코드를 다시 읽거나 실행 결과를 보고 실제 동작을 알게 되면(예: 앞선 코드가 먼저 예외를 던져 기대한 분기에 도달하지 못한다), **이번에 생성한 테스트 중** 틀린 기대를 가진 것을 고치거나 지운다. 같은 메서드를 같은 입력으로 호출하면서 서로 다른 예외를 기대하는 테스트를 둘 다 남기지 않는다. 실제로 도달할 수 없는 분기는 억지로 도달시키지 말고, 실제 동작을 기록하는 테스트 하나만 남기고 리포트의 "남은 공백"에 사유와 함께 적는다. (이 규칙은 이번에 생성한 테스트에만 적용한다. 기존 테스트와 운영 코드는 여전히 고치지 않는다.)

**경계값 정밀도.** 비교 연산(`<`, `<=`, `>`, `>=`)의 기준값이 상수·필드·`private` 메서드 인자이면 기준값 −1, 기준값, 기준값 +1을 각각 입력하는 테스트를 만든다. `private` 메서드는 직접 부를 수 없으니 그 값을 만들어 내는 public 입력으로 도달한다. `>`와 `>=`의 차이는 기준값과 같은 값이 들어간 입력으로 확인한다(같은 값이 여럿일 때 어느 쪽이 선택되는지 구분되게 단언한다). 한도 검사(크기·합계·오버플로)는 정확히 한도인 입력(성공)과 한도 ±1인 입력을 모두 만든다.

분기가 더 있으면 케이스를 더 만든다(위는 최소). 한 메서드의 `throw`가 여러 개면 `_exception`, `_exception2`처럼 각각 만든다.

**비교 연산이 없는 메서드의 경계.** `switch (type)`처럼 값마다 갈리기만 하는 메서드는 `<`·`>`가 없어도 `_boundary`가 필요하다. 입력 도메인의 끝값으로 호출해 결과를 단언한다: enum은 첫 값·마지막 값(그리고 `switch`가 다루지 않는 값이 있으면 그 값), 문자열·객체는 `null`·빈 값. 끝값을 정할 수 없는 메서드라면 가장 덜 흔한 값 하나를 고르고, 이유를 계획의 `note`에 적는다.

**enum 조합.** `switch`/`if` 체인이 enum 값(또는 enum × enum 같은 조합)으로 결과를 정하면 대표 2~3개로 끝내지 않는다. 가능한 조합을 모두 확인한다: 결과가 갈리는 조합은 모두, 거부·예외로 가는 조합은 값마다 최소 하나씩. 조합이 많으면 `@ParameterizedTest` + `@MethodSource`/`@CsvSource`로 순회하되, 이름은 `<메서드>_normalN`/`_exceptionN` 규칙을 따르는 별도 `@Test` 메서드로 두거나 각 조합을 개별 `@Test`로 만든다(점검기는 `@Test` 메서드 이름으로 센다). 조합표는 코드를 읽어 만들고, 어느 조합도 빠뜨렸는지 `switch`의 `case`와 대조한다.

## 클래스 종류별

- **Service:** BSM·Mapper를 `@MockitoBean`으로 스텁해 `when(bsm.getAccount(any(AccountIn.class))).thenReturn(...)`. 반환 VO(`Out.getInner()`)의 값과 `verify(bsm)` 호출을 단언한다. 입력 검증 실패 시 BSM이 호출되지 않음(`never()`)도 확인한다.
- **Controller:** Service는 실제 객체. `PBRequest<In>`를 만들어(`setData`, `setCommonHeader(new PBFixedHeader())`) 컨트롤러 메서드를 호출하고 `PBResponse.getData()`를 검증한다. 예외 케이스는 `PBExceptionHandlerAspect`가 켜져 있으면 반환된 오류 응답(`getData()`가 `null`, 헤더 `msgCode`)으로, 꺼져 있으면 Service가 던진 `PBOnlineException`이 그대로 나오는지(`assertThrows`)로 본다. 페이징 입력은 넘기는 `PBRequest`에 `setFixedPagingInfo`로 넣는다. 자세한 내용은 형식 규칙의 "Controller 테스트: 프레임워크 Aspect" 절을 따른다.
- **Mapper:** mock 없이 실제 DB(프로필)를 조회한다. **Mapper 메서드마다** 아래 케이스를 만들고, 쓰기 케이스는 같은 테스트 안에서 다시 조회해 단언한다. 키는 `UT_` 접두어 + 유일 값. 예외 케이스는 `assertThrows`.
  - select: 정상 2건(서로 다른 키로 찾는 경우 / 목록·페이징 결과), 경계(결과 없음, 선택 파라미터 null, 페이징 첫/마지막 페이지), 예외(필수 파라미터 null 등 → `DataAccessException` 계열).
  - insert/update/delete: 정상 2건(영향 행 수 1 + 다시 조회해 값 확인 / 다른 컬럼 조합), 경계(최대 길이 값, 대상 없는 키의 update/delete가 0건), 예외(중복 키·NOT NULL 위반 → `DuplicateKeyException`/`DataIntegrityViolationException`).
- **VO·상수·단순 위임:** 아래 "건너뛰기" 참고.

## 입력 만들기

- 필수 필드를 빠뜨리지 않는다(VO `Inner`의 `@Builder`/setter 확인). 누락하면 의도하지 않은 예외가 난다.
- 값은 VO의 `@FixedData(length=...)` 길이를 넘기지 않는다(경계값 케이스에서 의도적으로 넘기는 경우만 예외).

## 건너뛰어도 되는 경우와 skip_reason

계획 단계에서 대상 메서드를 건너뛰려면 `skip_reason`을 한 문장으로 적는다. 건너뛸 수 있는 것만:

- Lombok이 만든 getter/setter, 단순 getter·상수 반환 (`skip_reason: "Lombok getter, 분기 없음"`)
- 분기 없이 다른 클래스에 위임만 하는 메서드 (`skip_reason: "분기 없는 위임, 호출 대상이 mock이라 검증할 것이 없음"`)
- Mapper의 조건 없는 일괄 삭제 메서드(테이블 전체를 비우는 것): 롤백되는 트랜잭션 안이라도 다른 데이터소스·자동 커밋이면 실데이터를 지운다. `skip_reason`으로 건너뛸 수 있다 (`skip_reason: "조건 없는 일괄 삭제, 실데이터 보호"`).
- 본문이 없는 private 메서드(빈 훅)는 public 메서드 테스트로 함께 실행되므로 따로 만들지 않는다.

"어려워서", "시간이 걸려서"는 사유가 아니다. 건너뛴 메서드는 리포트에 사유와 함께 남는다.
