# 요구사항 기반 테스트 케이스 규칙 (TDD)

이 스킬은 **구현이 끝나기 전에** 요구사항만 보고 테스트를 먼저 쓴다. 대상 코드는 뼈대(클래스·메서드 시그니처)만 있고 본문은 비어 있거나 `UnsupportedOperationException`이다. 형식·mock·프로필·Mapper 규칙은 `docs/f-unit-test-format-rule.md`와 `templates/`를 그대로 따른다.

## 기대값은 요구사항에서만 정한다

- 뼈대의 본문, 이미 있는 구현, 다른 코드의 동작에서 기대값을 베끼지 않는다. 테스트가 요구사항을 검증해야지 현재 코드를 따라가면 TDD가 아니다.
- 입력 필드와 길이·필수 여부·타입은 뼈대의 VO(`@FixedData(length=...)`)와 요구사항(`--program`이면 FICO MCP의 입출력 명세)에서 읽는다. 명세의 필드 이름·길이·필수 여부·코드값이 기대값의 근거다.
- 요구사항이 정하지 않은 값(오류 코드, 메시지, 경계 수치)은 추측하지 않는다. 계획 단계에서 사용자에게 묻는다. 끝내 모르면 예외 타입만 단언하고 계획 `note`와 해당 테스트 주석에 "코드값 미정"이라고 적는다.
- 테스트가 지금 실패하는 것은 정상이다(뼈대는 구현이 없다). 통과시키려고 대상 코드를 고치지 않는다.

## 케이스 도출

요구사항을 문장 단위의 항목으로 나누고 **항목마다** 아래 케이스를 만든다. 이름은 `<메서드>_normal1`, `_normal2`, `_boundary`, `_exception` (같은 케이스가 더 있으면 `_boundary2`처럼 번호를 붙이고, `_boundary1`·`_exception1`은 쓰지 않는다).

| 케이스 | 도출 방법 |
|---|---|
| 정상 1 | 요구사항의 기본 성공 시나리오. 반환값과 mock 호출(`verify`)을 단언한다. |
| 정상 2 | 정상 1과 다른 입력·분기(선택 필드 있음/없음, 0, 여러 건). 복제 금지. |
| 경계값 | 요구사항의 수치·길이·건수 한도, 필수/선택, 빈 값. 한도와 한도±1을 본다. 수치 경계가 없으면 입력 도메인의 끝값(enum 첫·마지막 값, `null`·빈 값)으로 호출한다. |
| 예외 | 요구사항이 말하는 실패 조건(검증 오류, 조회 결과 없음, 외부 연동 실패). 요구사항에 없는 예외는 기대하지 않는다. |

- 한 항목이 여러 분기를 말하면 케이스를 더 만든다(위는 최소).
- 서로 모순되는 요구사항 항목(같은 입력에 다른 결과)은 테스트로 만들지 말고 계획 단계에서 사용자에게 알리고 고르게 한다.
- 요구사항이 없는 메서드는 만들지 않는다. 뼈대에 있어도 요구사항에 없으면 `skip_reason`을 적는다.

## 주석 (설명은 코드에 둔다)

생성한 테스트를 읽는 사람은 이 주석만 보고도 무엇을 왜 검증하는지 알아야 한다. 콘솔 설명은 짧게 하고 자세한 것은 주석에 남긴다.

- 클래스 Javadoc: 대상, 요구사항 출처(파일 경로, `--program` ID, "입력한 요구사항"), 요구사항 요약 한두 줄.
- **모든 `@Test` 바로 위**에 세 줄 주석(템플릿 형식)을 둔다. 주석이 없는 테스트는 점검에서 결함이다.
  - `// [요구사항] <항목 ID 또는 원문 한 줄>`
  - `// [시나리오] <정상 1 | 정상 2 | 경계 | 예외>: <입력과 상황>`
  - `// [기대] <요구사항이 말하는 결과: 반환값, 예외와 코드값, 호출되는 mock>`
- 기대값이 요구사항의 어느 숫자·코드에서 나왔는지 단언 옆에 한 줄 주석으로 적는다(예: `// 요구사항 3: 한도 1,000,000원`).
- 요구사항에서 정하지 못한 가정은 주석에 "가정:"으로 적는다.

## 건너뛰기

계획에서 대상 메서드를 건너뛰려면 `skip_reason`을 한 문장으로 적는다: 요구사항에 없는 메서드, Lombok getter/setter, 분기 없는 위임. "어려워서"는 사유가 아니다.
